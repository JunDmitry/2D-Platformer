## Task (what the coder was asked to do)

"implement skill effect that damage nearby enemies and on use effect damage executor health, but cannot kill executor, e.g. health cannot be zero"

I.e. a new skill effect that damages all enemies in an area (reusing the existing `AuraAreaDetector`/`IDamageable` pattern from `DoubleStrikeAreaEffect`), and also applies a self-cost damage to the executor's own health, with a guarantee that this self-cost can never bring the executor's health to zero (i.e. can never kill them).

## Blocker

Trigger 3 (new / changed public contract). `Assets/Scripts/Gameplay/Skill System/ExecutorData.cs` exposes the executor only through `IDamageable ExecutorDamageable` (`TakeDamage(float) : float`, `Assets/Scripts/Characters/IDamageable.cs`) and `IReplenishable ExecutorReplenishable` (`Replenish(float)`, `Assets/Scripts/Characters/IReplenishable.cs`). Neither contract exposes the executor's *current* health value. To guarantee "self-damage cannot reach zero", the effect must know the executor's current HP before applying damage (e.g. clamp the damage to `Current - 1`, or skip/reduce the hit if it would zero out). There is no way to read that through the contracts a skill effect is given.

- `Health.Current` (`Assets/Scripts/Gameplay/Health System/Health.cs`) exists and is exactly the value needed, but it is a property on the concrete `Health` `MonoBehaviour`, not reachable from `ExecutorData` without either (a) adding a new contract (e.g. something like `IHealthQueryable` with a `Current`/`Max` read), or (b) having the skill effect reach past `IDamageable`/`IReplenishable` and grab the `Health` component directly off the executor's `GameObject` — which bypasses the interface-driven contract convention in `paradigm.md` ("Cross-component contracts go through interfaces where the concrete type shouldn't be assumed").
- `Player.TakeDamage`/`Enemy.TakeDamage` (`Player.cs:54`, `Enemy.cs:47`) both already compute and return "damage actually dealt" (`oldHealth - _health.Current`), which lets a *caller* know how much a hit reduced health by, but that is only known *after* the hit — too late to prevent going to zero on that same call.
- Same shape as `docs/architecture/architect-inbox/c2.md` (still open): a skill effect needs a capability on the executor that today only exists on the concrete `Health` component, not on any interface the Skill System is allowed to depend on.

## Impact if not done

The user cannot get a guaranteed non-lethal self-cost skill effect. Any implementation that skips this (e.g. the effect grabbing `GetComponent<Health>()` directly off the executor, or assuming a fixed damage amount is "probably safe") would either bypass the interface-driven contract convention or fail to actually guarantee the executor survives (e.g. two effects stacking self-damage in the same frame, or a config damage value the effect author sets higher than current health).

## Proposed shape (optional)

Not prescribing, but for reference:

1. A new small interface, e.g. `IHealthQueryable { float Current { get; } float Max { get; } }`, implemented by `Player`/`Enemy` (delegating to their existing `_health` field), added to `ExecutorData` alongside `ExecutorDamageable`/`ExecutorReplenishable`. The effect would then read `executorData.ExecutorHealthQueryable.Current` and clamp its own self-damage to `Current - 1` (or `Max(Current - 1, 0)` skip-if-already-at-1) before calling `TakeDamage`.
2. Alternatively, extend `IDamageable` itself with a `Current`/`Max` read — but that is a wider-reaching change since `IDamageable` is implemented by anything damageable (not just executors), including enemies hit by other effects that don't care about survive-guarantees.

Also note: the "damage nearby enemies" half of this task (reusing `AuraAreaDetector.FindTargetsInRadius` + `IDamageable.TakeDamage`, same pattern as `DoubleStrikeAreaEffect`) is not architecturally blocked on its own — only the self-cost-with-floor half is.
