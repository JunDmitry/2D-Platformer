## Task (what the coder was asked to do)

"implement knockback area effect placed on mouse point on cast with max range from player position with concrete duration. Knockback in number per second"

I.e. a new skill effect that, on cast, resolves an area at the mouse cursor's world position (clamped to a max range/distance from the caster), pushes every target inside that area away over a fixed duration, at a knockback rate expressed per second.

## Blocker

Trigger 3 (new/changed public contract) and, secondarily, trigger 2 (module boundary / cross-module behavior mismatch).

- The only cross-component contract that `Player` and `Enemy` both implement is `IDamageable` (`Assets/Scripts/Characters/IDamageable.cs`), which only exposes `TakeDamage(float) : float`. There is no way for a skill effect to apply force/displacement to a target through an existing contract. A knockback effect needs to push a target, not damage it — this requires a **new public contract** (e.g. something like `IKnockbackable`) that `Player` and `Enemy` would need to implement, since skill effects only see targets through `AuraAreaDetector.FindTargetsInRadius(ExecutorData) : List<IDamageable>` (`Assets/Scripts/Gameplay/Skill System/AuraAreaDetector.cs`).

- Even if such a contract existed, the two movers have incompatible physics models:
  - `PlayerMover` (`Assets/Scripts/Characters/Player/PlayerMover.cs`) drives `Rigidbody2D.velocity` every `FixedUpdate` via `Move(direction)`, called every frame from the state machine — an external `AddForce`/velocity nudge would be overwritten almost immediately by the next `Move` call.
  - `EnemyMover` (`Assets/Scripts/Characters/Enemy/EnemyMover.cs`) does not use `Rigidbody2D` physics at all — it directly sets `transform.position` via a coroutine (`MoveTo`) started fresh on every `Move(direction)` call, competing with the state machine's own movement coroutine.
  
  So "push a target away for a duration at N/sec" would behave completely differently (or not survive a single frame) on Player vs Enemy without changes to how each mover handles being overridden externally. That is more than a pure additive contract; it is a behavior/module change in `Characters/Player` and `Characters/Enemy`.

## Impact if not done

The user cannot get a knockback skill effect at all — every viable implementation path requires either a new cross-component contract, a change to how Player/Enemy movers cede control to external forces, or both. Any implementation that skips this (e.g. silently moving `transform.position` from the effect, bypassing `IDamageable`/movers) would be a paradigm violation (bypassing the interface-driven contract convention) and would conflict with whichever mover is actively driving the same object that frame.

## Proposed shape (optional)

Not prescribing, but for reference, two directions observed while investigating:

1. A new `IKnockbackable` interface (e.g. `void ApplyKnockback(Vector2 direction, float speedPerSecond, float durationInSeconds)`) implemented by `Player` and `Enemy`, with each mover exposing a way to temporarily suspend/override its own movement while an external knockback is active (e.g. a `Mover.IsOverridden` flag or similar), so `PlayerMover.Move`/`EnemyMover.Move` don't fight the effect.
2. Alternatively, folding "knockback" into `Mover` itself (base class) as a shared capability, so both `PlayerMover` and `EnemyMover` get a consistent way to receive an external push regardless of how each drives its own movement day-to-day.

Also note: resolving the "mouse point clamped to max range from player" placement itself is new code (screen-to-world via `Camera.main`, clamped by `Vector2.ClampMagnitude`), not architecturally blocked — it only becomes relevant once the target-affecting contract exists.

## Resolution (filled by architect)

- **Date / session:** 2026-09-24, sess-2026-09-24-architect.
- **Decided:** [ADR-0002](../adr/0002-knockback-capability.md) — a new `IKnockbackable` interface (`ApplyKnockback(Vector2 direction, float speedPerSecond, float durationInSeconds)`) implemented by `Player` and `Enemy`, delegating to their own `Mover`. `Mover` gained a `protected bool IsOverridden` flag and an abstract `ApplyKnockback(...)`; `PlayerMover.Move`/`EnemyMover.Move` are now no-ops while `IsOverridden` is true, so the state machine's per-frame `Move` calls stop fighting an active knockback. Each mover implements `ApplyKnockback` using its own existing physics model — no unification of the two movers' physics models was done (that was evaluated as Option B and rejected as disproportionate to this request; tracked as an open hotspot in `hotspots.md`).
- **What the coder can now do:** implement the knockback `ISkillEffect` (mouse-point area resolution, clamped to max range from the caster, per-second knockback rate) using `AuraAreaDetector.FindTargetsInRadius(executorData)` to get `List<IDamageable>`, then for each target check `if (target is IKnockbackable knockbackable) knockbackable.ApplyKnockback(direction, speedPerSecond, durationInSeconds);`. No detector or `IDamageable` change needed — `IKnockbackable` is a separate, optional interface a target may or may not implement. Build verified green (`dotnet build "2D Platformer.sln"`, 0 errors).
