## Goal

Turn the single hard-coded `VampireSkill` pipeline into a reusable, data-driven, multi-skill framework.

## Context

- Orientation: `docs/architecture/orientation/index.md`
- Relevant subfiles: `modules.md` (Gameplay / Skill System section), `hotspots.md` (Skill System + `AuraSingleDetector.FoundTargets` null-yield entries)
- Related ADRs: ADR-0001 (to be created)

Flagged by orientation `hotspots.md`: `VampireSkill` hard-codes one skill's duration/cooldown/event lifecycle; `NearestVampireDamageEffect` and `AuraSingleDetector` are single-purpose and non-reusable; no shared base type, no registry, no data-driven config; a second skill would require copy-pasting `VampireSkill`'s coroutine logic.

User answers (via AskUserQuestion, 2026-09-21):
- Support multiple skills (generalize, not just patch).
- Skill tuning data (duration/cooldown) becomes ScriptableObject-based.
- Character holds a generic skill list/loadout, not fixed named slots.

## Inputs

- Files read: `Assets/Scripts/Gameplay/Skill System/VampireSkill.cs`, `AuraSingleDetector.cs`, `NearestVampireDamageEffect.cs`, `ExecutorData.cs`, `Assets/Scripts/Characters/Player/Player.cs`, `Assets/Scripts/Characters/Player/InputReader.cs`, `Assets/Scripts/UI/VampireView.cs`, `Assets/Scenes/SampleScene.unity` (serialized values for the existing `VampireSkill` GameObject: duration=6, cooldown=4, damagePerSecond=15, healingPercentage=1, radius=1.4, layer bit=64).

## Options considered

### Option A — Composed `Skill` component (chosen)
- Pros: smallest change; matches project's composition-over-inheritance convention; one class to reason about.
- Cons: no dedicated extension point if a future skill needs different lifecycle semantics (only different effects are supported cleanly).

### Option B — `Skill` base class + subclasses
- Pros: clean extension point for skills with genuinely different lifecycle behavior.
- Cons: MonoBehaviour inheritance adds Inspector/Awake-chain friction; no current skill needs it.

### Option C — Fully data-driven `SkillDefinition` assets + generic executor
- Pros: most reusable/shareable across prefabs; skills become near-pure data.
- Cons: biggest refactor; moves effect/detector logic out of MonoBehaviour-land, deviating further from the project's current all-MonoBehaviour convention; detector loses its scene-object Gizmo.

### Chosen
"A: Composed Skill (Recommended)" — user selected via AskUserQuestion, 2026-09-21.

## Decision summary

Replace `VampireSkill` with a generic `Skill` MonoBehaviour that owns the execute/dedupe/duration-tick/cooldown/event lifecycle, reads duration/cooldown from a new `SkillConfig` ScriptableObject, and delegates the per-tick effect to an injected `ISkillEffect` (extracted from `NearestVampireDamageEffect`). `Player` holds a `Skill[]` loadout instead of a single `_firstSkill` field. Bundled in the same touch: fix the `AuraSingleDetector.FoundTargets` null-yield API oddity already flagged in `hotspots.md`, since it sits in the same file being generalized.

## Plan

1. Add `ISkillEffect` interface (`IEnumerator Run(ExecutorData)`).
2. Add `SkillConfig : ScriptableObject` (duration, cooldown) + `VampireSkillConfig.asset` seeded with the scene's current values (6s / 4s).
3. Rename `VampireSkill` → `Skill`; replace duration/cooldown fields with `_config : SkillConfig`; retype `_effect` to a validated `ISkillEffect`-implementing `MonoBehaviour` reference.
4. Fix `AuraSingleDetector`: replace `FoundTargets(...) : IEnumerable<IDamageable>` (nullable yield) with `FindNearestTarget(...) : IDamageable` (nullable return). Update `NearestVampireDamageEffect` (now implementing `ISkillEffect`) accordingly.
5. Update `Player`: `_firstSkill : VampireSkill` → `_skills : Skill[]`; trigger by index.
6. Update `InputReader`: generalize the single `Alpha1` skill key into an indexed key table (`IsSkill(int index)`), no scene changes needed (keys stay code-defined consts, matching existing convention).
7. Rename `VampireView` → `SkillView`; retype its field from `VampireSkill` to `Skill`.
8. Edit `Assets/Scenes/SampleScene.unity`: swap the `VampireSkill` component's `_durationInSeconds`/`_cooldownInSeconds` fields for a `_config` reference to the new asset; convert `Player`'s `_firstSkill` reference into a one-element `_skills` array.
9. Update orientation subfiles (`modules.md`, `hotspots.md`) and bump `.meta.json` version.
10. Write ADR-0001 for the new ScriptableObject-config + `ISkillEffect` pattern (new to the project — paradigm addition, not an exception).

Each step verified by re-reading the edited file / diff before moving to the next.
